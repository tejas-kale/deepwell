Before Sunday: four things that take minutes now and hours if left

Tick them off here (the ticks stay in this browser).

The steps, with the reasoning beside each

1. Install and run the tests

2 minMac terminal
cd ~/Code/deepwell/eval && python3 -m venv .venv && .venv/bin/pip install -e '.[test]' && .venv/bin/pytest -q
Check18 passed. These include copies of the app's own validator tests, so a failure means the Python has drifted from the Swift.

Why

The harness re-implements three pieces of the app in Python (reading item files, deciding what's eligible, validating a menu) so it can run on Colab. The tests mirror MenuTests.swift case for case; passing them is the evidence that "usable" here means what the app would accept.

2. Put the code in Drive and name the folder

1 minFinder, then terminal

Copy ~/Code/deepwell/eval to My Drive/deepwell-eval/eval. Then set D for this terminal (your Drive folder name differs):

D="$HOME/Library/CloudStorage/GoogleDrive-/My Drive/deepwell-eval"

Why

Drive is the one folder both machines see. The Mac writes the frozen prompts and Sonnet's menus; Colab reads the prompts and writes Gemma's menus beside them; the Mac judges both. No copying back and forth, and a Colab disconnect loses nothing.

The cost: your item titles and summaries sit in Drive and pass through Colab. Fine now that privacy isn't the goal of this study.

3. Freeze the pilot

1 minOpen Deepwell first so the library is synced
.venv/bin/deepwell-eval prepare --library "" --run "$D/runs/pilot"
Check the printoutAbout 178 eligible items; few without a summary; your recent topics; settings read from the Mac (and which ones you changed from the defaults).

Why 20 subsets of 60 items

A menu is 3 to 5 bundles of about 11 items, so each slice needs about 60 items to leave the model real choices. 20 slices is enough to see a 15-point gap between model sizes; 100 would be needed to pin down "as good as Sonnet", which is the full study's job.

Why freeze: every model gets byte-identical prompts, and the run folder refuses to be prepared twice, so nobody (me included) can re-roll the slices after seeing results.

Why no held-out pool: the pilot trains nothing, so nothing can leak. A 30% hold-out of 178 items (about 53) couldn't fill one menu anyway.

4. Sonnet builds the reference menus

15 minabout $3Start step 5 while this runs

One request first, to see it work:

.venv/bin/deepwell-eval generate --run "$D/runs/pilot" --arm sonnet --backend anthropic --limit 1

Then the other 39:

.venv/bin/deepwell-eval generate --run "$D/runs/pilot" --arm sonnet --backend anthropic

Why Sonnet is the baseline

It's what Deepwell ships today, called exactly as the app calls it: same prompt, same schema, same effort. The question is "could I swap it out?", so it's the bar to clear.

One attempt, no fallback. The app retries once on a bad reply; the harness doesn't, so usable rates are first-try rates for every model alike. And if Sonnet declines a request, that counts as a failure rather than quietly becoming another model's answer.

5. Gemma 4 on Colab

2–2.5 h unattendedRuntime › Change runtime type › an 80 GB GPU

Upload eval/colab_gemma.ipynb (File › Upload notebook) and run the cells top to bottom:

  1. The model check: all four ids should print ok.
  2. The smoke test: one menu from E4B. reasoning_chars must be above 0 and raw should be a JSON menu.
  3. Delete outputs/smoke-e4b.jsonl from the run folder.
  4. The full loop. If Colab disconnects, run it again; finished requests are skipped.

Why these four models

One family, so size is the only thing that changes. E4B, 12B and 31B are a dense ladder. 26B A4B is the interesting one: 25B parameters stored, only 3.8B used per token. If it matches 31B and beats E4B, stored knowledge is what this task needs, not compute.

Why thinking on: Sonnet thinks at medium effort; switching Gemma's off would test "thinking or not" instead of "size". The smoke test confirms the switch actually worked.

Why a second, unconstrained pass (-raw arms): every arm gets the JSON shape enforced so quality is compared fairly, but a small model's raw format failure rate is a finding in its own right.

Why full precision here: it answers the research question cleanly. Whether 4-bit on the Mac holds up is a separate check for the full study.

6. Opus judges, blind

30 minabout $20–25After steps 4 and 5 finish and Drive has synced
.venv/bin/deepwell-eval judge --run "$D/runs/pilot"

If any calls fail, run the same command again; finished verdicts are skipped.

Why an LLM judge, and why both orders

Eight comparisons on 20 slices is 160 pairs: about three hours of careful rating for one person, and boredom makes the later ratings noise. Opus takes the volume; my 15 ratings in step 8 test whether it can be trusted.

Each pair is judged twice with A and B swapped. A win only counts if both verdicts agree; otherwise it's a tie. That cancels the judge's habit of preferring whichever menu comes first.

The judge always sees titles, tags and summaries, even for the titles-only arms, so it can tell whether a grouping makes sense.

7. Export 15 blind pairs

1 min
.venv/bin/deepwell-eval pairs --run "$D/runs/pilot" --n 15
Don't openrater/pairs.key.json. It says which model made which menu.

Why 15, spread this way

The pairs are drawn evenly across the four models and both inputs, so agreement with Opus isn't measured on one model alone. 15 is enough to catch a judge that's badly off; the full study raises it to 40.

8. Rate them

30 minAny browser

Open eval/rater/index.html, load runs/pilot/rater/pairs.json, and for each pair ask: which menu would serve me better this week? Keys A, B, T; arrows to move. Press Download ratings at the end and move ratings-pairs.json into runs/pilot/rater/.

Use Tie only when neither is clearly better. Bundle lengths were already enforced by the app's rules, so don't judge length.

Why my ratings matter more than Opus's

"Good" here means good for me. If Opus and I disagree often, the full study's 700 verdicts would measure Opus's taste, not mine.

There's a second check: if my win-or-tie rate for Gemma is clearly higher than Opus's on the same pairs, Opus favours Sonnet's style (same family), and its verdicts understate the small models.

9. Read the report

15 min
.venv/bin/deepwell-eval report --run "$D/runs/pilot" --ratings "$D/runs/pilot/rater/ratings-pairs.json"

It writes runs/pilot/report.md. Read it in this order:

  1. Hard constraints: truncated should be 0 everywhere.
  2. Pilot decision: the three rules above, each marked met or not met.
  3. Topic quality: win-or-tie with its interval, per model and input.
  4. Does the input carry the knowledge? The gap to Sonnet with titles only against the gap with summaries.

How to read the knowledge table

If a small model's gap shrinks a lot when it gets summaries, the input carries what it lacks: summaries are doing the work, and a small model is enough. If the gap stays wide even with summaries, the large model's background knowledge is what matters.

Then follow the yellow decision tree at the top. It was written before the data existed; the point is not to argue with it on Sunday evening.

Why it's built this way: decisions from the grilling

Each was argued through on 26 November. The rejected option is kept so I remember why it lost.

If something breaks

A model id prints MISSINGFix the id in the notebook's MODELS cell from the model's Hugging Face page. Only the 31B id was checked in advance.
reasoning_chars is 0Thinking didn't switch on. Fix EXTRA_BODY for Gemma 4's chat template before the full loop, or the Gemma arms ran without thinking.
Colab gives a 40 GB GPUThe notebook runs 26B A4B and 31B at 8-bit and names them -fp8. Note it in the write-up; it's a different model from full precision.
Colab disconnectsReconnect, re-run the setup cells, then the loop. Finished requests are skipped.
truncated above 0 in the reportReplies ran out of room. Re-run that model under a new arm name with a larger --max-tokens.
Judge calls failRun judge again. Only missing verdicts are requested.
